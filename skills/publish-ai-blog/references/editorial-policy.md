# AI 博文编辑与多语言规范

## 研究账本

每条可核验陈述至少记录：

- `claim`：准备写入文章的准确陈述。
- `event_date`：事件实际发生或功能实际开放的日期。
- `source_date`：来源发布或最后更新日期。
- `source_type`：公告、文档、论文、模型卡、代码、评测、媒体、社交、访谈或社区。
- `url`：直接指向原始材料的稳定链接。
- `support`：支撑陈述的原文、表格、代码或测试结果。
- `scope`：地区、版本、模型 ID、套餐、硬件、提示、数据集或其他适用条件。
- `confidence`：高、中、低，并解释不确定性。

将同一来源复制到多个网站视为一条证据，不视为独立交叉验证。

## 默认写作模式与范围

- 将仓库和博客系统视为发布渠道，不把它们自动变成文章主题。
- 用户未指定文章类型时，默认写独立、完整的大模型或 AI 深度分析，而不是短新闻快讯。
- 除非用户明确要求项目或 API 网关视角，否则不要在标题、摘要、正文、实践建议或结论中加入本项目、统一网关、供应商路由、计费、接入方式、兼容性或“本项目已支持”等内容。
- 文章可以面向一般 AI 读者、模型使用者、开发者、研究者或行业观察者；不需要为了发布在本项目博客中而制造项目关联。
- 材料确实不足时不要注水。说明证据缺口、继续研究，或在用户明确接受后改成简报。

## 选题评分

每项按 0 至 3 分评分，优先选择总分高且证据充分的主题：

| 维度 | 0 分 | 3 分 |
| --- | --- | --- |
| 新鲜度 | 已过时或只是旧闻翻炒 | 最近发生且仍在发展 |
| 读者影响 | 对模型使用者或 AI 行业没有实质意义 | 明显影响能力判断、模型选择、成本、工作方式或行业方向 |
| 证据质量 | 只有传闻或单条帖子 | 多个原始来源和独立验证 |
| 可写深度 | 只能写几句公告 | 有技术、行业、限制和实践角度 |
| 长期价值 | 很快失效 | 数月后仍有参考价值 |

避免为了追热点牺牲证据质量。没有足够材料时改写成“已知与未知”简报，或暂缓发布。

## 推荐结构

标题字段承担页面 H1，正文从 H2 开始。默认深度稿根据主题调整，通常用 8 至 12 个实质章节覆盖：

1. 导语：在前两段说明谁、何时、发布了什么，以及为什么值得关注。
2. 背景与时间线：交代前代模型、相关论文、竞争格局或事件演进。
3. 技术变化：模型、训练、推理、上下文、工具、数据、硬件、API 行为或能力细节。
4. 数据与评测：写明结果、口径、版本、方法和厂商自报属性。
5. 独立证据：加入第三方评测、复现、实际使用反馈或可靠媒体核验，并解释与官方材料是否一致。
6. 与前代或竞品相比：只在口径足够一致时比较，并解释差异来自哪里。
7. 成本与现实影响：讨论 Token、延迟、工具调用、工作流、部署或使用成本；不要求强行写 API 网关。
8. 安全、限制和反例：说明失败模式、评测缺陷、未开放能力、风险和不适用场景。
9. 适用场景与选择建议：把证据转化为克制、可执行的判断。
10. 未知项：列出仍无法由现有证据回答的问题。
11. 结论：总结最重要的判断，不重复整篇内容。
12. 资料来源：列出最重要的原始材料和独立来源。

只有用户明确要求快讯或简报时，才使用约 1000 至 1600 个拉丁语系单词，或约 2000 至 3500 个中日韩字符。默认深度分析通常写 2500 至 4500 个拉丁语系单词，或约 5000 至 9000 个中日韩字符；技术和数据确实丰富时可以更长，不为命中字数删掉有价值的背景、方法或限制。

字数只是过短预警，不是质量本身。深度稿还应满足：

- 资料来源通常为 6 至 12 个，优先覆盖官方公告、技术文档或模型卡，以及至少两个可获得的独立证据来源。
- 研究账本通常记录至少 12 条会进入正文的重要事实，并区分官方主张、独立结果和作者分析。
- 每组关键数字都解释测试条件、比较口径和现实意义，不只堆表格。
- 每个主要结论都有证据、限制或反例，避免把同一观点换词重复。
- 主稿低于默认范围时，继续补充可验证的背景、方法、影响和限制；若没有足够材料，明确报告而不是填充空话。

## 标题、摘要与 SEO

- 使用具体名词和实际变化，避免“重磅”“炸裂”“史诗级”“彻底颠覆”等点击诱导。
- 标题不承载无法证明的结论；把条件和不确定性留在标题中需要时明确写出。
- 摘要独立成文，包含事件、时间、最重要变化和读者意义，不以“本文将介绍”开头。
- slug 使用稳定的英文主题，不塞入发布日期，除非日期本身是事件身份的一部分。
- 标签控制在 3 至 6 个，优先使用模型族、厂商、主题和 API 能力，避免同义标签堆叠。
- 快速变化的文章在正文显著位置写明资料截止日期。

## 引用与版权

- 引语必须逐字来自原始帖子、视频、文字稿、论文或文章。无法核对原文时改为有归属的转述。
- 给出说话人、当时身份、场合和日期。个人观点不能改写为组织承诺。
- 翻译引语时说明“译文”，并在链接附近保留原文关键短语；不要改变语气强度。
- 只引用支持论点所需的短句。长篇内容用自己的话总结并链接原文。
- 不复制完整表格、图像或大段文字，除非许可明确且确实必要。

## 数字、跑分与比较

- 同时写出单位、模型版本、测试集版本、日期、硬件、提示策略和是否厂商自报。
- 不比较口径不同的价格、吞吐、首 token 延迟、上下文或基准分数。
- 说明排行榜置信区间、样本量、模型别名、提示优化、数据污染和代理框架差异。
- 将“在某项测试领先”写成局部结论，不扩展为“全面最强”。
- 对估算值标注计算方法；不要用模型生成的数字替代可追踪数据。

## 项目与网关边界

- 默认完全不写项目或网关相关内容，即使主题本身涉及模型 API、价格或工具调用，也先从模型和 AI 行业本身展开。
- 只有用户明确要求“结合本项目”“分析网关影响”“说明接入方式”或同等范围时，才加入统一网关、供应商路由、计费、流式响应、多模态处理或项目兼容性。
- 获得该明确要求后，仍只有在仓库适配器、模型配置或线上接口中实际验证，才能写“本项目已支持”；未支持时使用条件式表达，不作上线承诺。
- 不把私有运营配置、内部域名、凭据、未公开路线图或本地说明文件内容写进公开文章。

## 多语言规则

### 语义一致

- 以核验完成的主稿为事实源。先修改主稿，再同步所有语言，不在单个译文中偷偷增加新事实。
- 保持章节对应、关键数字一致、来源 URL 可追踪、风险提示不缺失。
- 允许为目标语言重排句子、解释本地读者不熟悉的缩写，并使用当地常见标点和日期格式。
- 产品名、模型 ID、API 路径、JSON 字段、代码、命令、版本号和组织正式名称保持原样。

### 语言质量

- `zh`：使用自然简体中文技术表达，避免翻译腔和过度口语化。
- `en`：使用简洁的国际技术英语，避免把中文成语直译。
- `es`：使用中性国际西班牙语；技术名词优先参考厂商西语文档。
- `fr`：保持法语句法和术语一致，参考 `docs/translation-glossary.fr.md`。
- `ru`：使用自然技术俄语，参考 `docs/translation-glossary.ru.md`，不要机械音译已有通用译名。
- `ja`：使用自然、克制的技术日语，避免逐句照搬中文语序。
- `vi`：使用一致的越南语技术术语，保留广泛使用的英文 API 和模型名称。

### 对齐检查

- 比较七种语言的标题、摘要、H2/H3 数量、表格行数、列表项、数字、代码块和来源链接。
- 检查否定词、条件词、概率和时间状态，防止“可能”被翻成“已经”。
- 检查所有语言是否都有“限制”和“资料来源”部分。
- 朗读或回译高风险句子，包括价格、法律、性能、安全和直接引语。

## Markdown 兼容性

为了让 React 页面和服务端 SEO HTML 表现一致，只使用：

- H2 至 H6 标题；
- 普通段落；
- 单层有序或无序列表；
- 简单引用块；
- 行内代码和围栏代码块；
- 简单 GFM 表格；
- Markdown 链接、粗体和斜体。

避免原始 HTML、脚注、任务列表、嵌套列表、复杂指令、正文 Markdown 图片和依赖客户端插件的语法。使用文章级 `cover_image` 展示主图。

数据较多时使用简单 Markdown 表格，并在表格前后解释统计口径、条件和结论。当前未验证正文图片支持时，不把图表渲染成 Markdown 图片；不得为了视觉效果生成不存在的数据、坐标轴、标签或来源。

## 封面图

- 优先使用厂商明确允许新闻使用的媒体素材、自有图片或原创生成图。
- 记录来源、许可和必要署名。无法确认许可时不用该图。
- 不使用带有第三方水印、误导性界面、伪造人物言论或看似真实但并不存在的产品截图。
- 原创封面默认使用 16:9 宽幅构图，画面要与文章主题相关，并避免可读文字、标志、商标、虚构数据和伪造产品界面。
- 将最终图片保存到草稿目录，记录生成工具、日期、提示词或编辑意图、尺寸和 SHA-256；不要移除已有的来源或 AI 生成元数据。
- 本地草稿阶段不执行远端上传。用户授权线上写入后，使用项目控制的持久地址，避免临时签名 URL；确认匿名 HTTPS `200`、正确图片类型和文件一致性后再填写 `cover_image`。

## 发布前检查

- 资料截止日期清楚，所有关键事实都能回到原始来源。
- 至少一个独立来源验证厂商的重要主张，或文章明确说明尚无独立验证。
- 标题和摘要没有超出正文证据。
- 默认深度稿达到内容范围和证据密度要求；没有用重复表达凑篇幅，也没有因篇幅目标省略重要方法、限制或反例。
- 未经用户明确要求，文章没有加入项目、网关、路由、计费、兼容性或接入状态。
- 引语、数字、表格和比较包含上下文与条件。
- 所有语言内容完整且事实对齐。
- 没有秘密、内部信息、占位符、侵权大段复制、未经许可的封面或虚构图表数据。
- payload 保持完整翻译集合，slug、标签、状态和时间正确。
- 用户已明确授权正式上线，或文章保持草稿。
